# v2.6 In-App Onboarding Wizard — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A resumable, skippable 7-step in-app onboarding wizard at `/welcome` that captures the full household profile, motivations, a first bill, and service preferences — with completion shared between the app and the bot's lite flow.

**Architecture:** Pure step logic in `lib/onboarding/steps.ts` (tested like `lib/nav/userNav`), a shared `markOnboarded` write used by both the new API route and the bot handler, wizard state derived from the profile itself (no state table), and thin screens in the established kit/shadcn language. All data lands in existing `profiles` JSON columns.

**Tech Stack:** Next.js 15 App Router, Drizzle+SQLite, shadcn/ui + kit components, vitest (node env, in-memory SQLite via `makeTestDb()`).

**Spec:** `docs/superpowers/specs/2026-10-03-v2.6-onboarding-wizard-design.md`

## Global Constraints

- Persian-only copy, informal tone («شما»/«تو» as in existing `copy.ts`); all new UI strings live in `web/src/content/copy.ts`.
- No new dependencies. No schema migrations. No changes to the chat persona.
- Works in webviews (no pushState inside the wizard) and browser deep links.
- House test style: node-level vitest, in-memory SQLite (`makeTestDb()`); structural wiring tests (fs reads) follow `tests/userAppNav.test.ts` precedent.
- Every commit ends with the attribution line per repo convention.
- `web/` is the app root: run tests with `cd web && npx vitest run`, types with `npx tsc --noEmit`, build with `npm run build`.

## Review Focus

Five input classes the task tests do not fully exercise — each pinned by the named test:

1. **Legacy string-typed numbers:** old writes stored `occupants`/`area_m2` as strings ("۳"/"3"); mappers must coerce both. → `tests/onboardingSteps.test.ts` "draftFromProfile coerces legacy string numbers" (Task 2).
2. **Behaviour shallow-merge clobbering:** writing `service_prefs` must not erase sibling behaviour keys (`onb_step`, memory-related keys). → `tests/profileParts.test.ts` "behaviour merge preserves sibling keys" (Task 1).
3. **Double completion:** completing twice fires exactly one `onboarding_completed` event and keeps the first `completedAt`. → `tests/onboardingComplete.test.ts` (Task 3).
4. **Completed user hitting `/welcome`:** redirects to `/home` instead of re-running. → `tests/onboardingWiring.test.ts` (Task 8).
5. **Bot-first users:** a user completed via bot-lite (`source: "bot"`) must never be redirected to `/welcome`. → same wiring test file (Task 8).

import { emitAppEvent } from "@/lib/events";
import { getProfileRow, updateProfileParts } from "@/lib/profile/parts";
import type { schema, type DB } from "@/lib/db"; // import schema & DB the same way handler.ts does

type ProfileRow = typeof schema.profiles.$inferSelect;

export function isOnboarded(row: ProfileRow | undefined): boolean {
  if (!row) return false;
  const behaviour = JSON.parse(row.behaviour ?? "{}") as { onboarding?: { completed?: boolean } };
  return behaviour.onboarding?.completed === true;
}

export function markOnboarded(db: DB, userId: string, source: "app" | "bot"): { alreadyCompleted: boolean } {
  const row = getProfileRow(db, userId);
  if (isOnboarded(row)) return { alreadyCompleted: true };
  updateProfileParts(db, userId, { behaviour: { onboarding: { completed: true, completedAt: Date.now(), source } } });
  emitAppEvent("onboarding_completed", { userId, source });
  return { alreadyCompleted: false };
}
